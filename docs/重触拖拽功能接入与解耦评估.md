状态：核心功能已实现并通过模块级回归测试；真机验收、传统 View 的完整事件所有权和若干性能边界仍需继续验证。

## 1. 结论先行

当前系统已经支持：

> 任意位于 HeavyDragHost 内的 Compose UI，只要声明 Modifier.heavyDraggable()，就能获得“轻触点击、重触确认后拖动”的能力；任意 UI 也可以声明 heavyDropTarget() 或 heavyOverlapTarget()，接收拖放和重叠事件。

当前架构属于“核心高内聚、模块低耦合、应用层有意适配耦合”：

- 触摸 SDK 不知道 UI、拖动源、目标或业务对象。
- 纯领域拖拽层不依赖 Android、Compose 或 SDK。
- SuperApp 只在防腐适配器中把 SDK 分类结果转换为通用拖拽分类结果。
- 业务组件通过声明式 Modifier 和回调接入，不需要修改状态机。

综合评价：

| 维度 | 当前评价 | 说明 |
|---|---:|---|
| 核心状态机内聚性 | 9/10 | 手势状态、取消、命中和事件顺序集中管理 |
| UI 适配层内聚性 | 8/10 | 平台事件、布局边界和视觉位移职责清楚 |
| SDK 与拖拽层低耦合 | 9/10 | 只通过通用分类网关连接 |
| 业务层低耦合 | 8/10 | 新组件通常只声明 Modifier 和业务回调 |
| 整体成熟度 | 8.3/10 | 主要扣分来自 View 事件流、并发和类型安全边界 |

## 2. 完整接入链路

~~~mermaid
flowchart LR
    user[用户触摸] --> host[HeavyDragHost\nCompose 根入口]
    host --> runtime[HeavyDragRuntime\nMotionEvent 生命周期]
    runtime --> bridge[AispectHeavyTouchBridge\nSuperApp 防腐层]
    bridge --> sdk[AispectTouchClassifier\n独立 AAR]
    sdk --> result[四分类结果\n轻触/重触/置信度/gestureId]
    result --> bridge
    bridge --> runtime
    runtime --> coordinator[HeavyDragCoordinator\n纯领域状态机]
    coordinator --> source[HeavyDragSource\n声明可拖动组件]
    coordinator --> target[HeavyDragTarget\nDrop Zone / Overlap]
    source --> sourceCb[点击/拖动/取消回调]
    target --> targetCb[进入/离开/放下/重叠回调]
    sourceCb --> business[业务逻辑]
    targetCb --> business
~~~

### 2.1 事件顺序

1. 用户在已注册 source 边界内触发 ACTION_DOWN。
2. Compose 根通过 motionEventSpy 观察事件，HeavyDragRuntime 为该序列建立 gestureId。
3. Runtime 将事件交给 SDK 适配器和 HeavyDragCoordinator。
4. SDK 持续采集触摸与 IMU 数据，在后台完成模型推理。
5. SDK 返回当前 gestureId 的分类结果。
6. Coordinator 只接受与当前手势、指针和时间窗口匹配的结果。
7. 轻触在 ACTION_UP 时只触发一次 onClick。
8. 重触且置信度达标后进入 DRAGGING，后续 MOVE 才改变源组件位置。
9. Coordinator 根据几何关系通知 Drop Zone 或 Overlap Target。
10. ACTION_UP、ACTION_CANCEL、多指、失焦或卸载时产生唯一终态并清理会话。

## 3. 任意 UI 的接入合同

### 3.1 必须满足的前置条件

任意 Compose 组件要获得重触拖拽能力，必须满足：

1. 组件位于同一个 HeavyDragHost(runtime) 内。
2. 应用通过 HeavyDragRuntimeProvider 注入一个运行时。
3. sourceId 在当前 Root 内稳定且唯一。
4. 组件能持续提供有效的布局 bounds。

缺少 Provider 时，业务 UI 应回退到原有点击、长按和滚动逻辑；缺少 Host 时，Modifier 无法获得统一坐标空间。

### 3.2 声明拖动源

~~~kotlin
Box(
    modifier = Modifier.heavyDraggable(
        coordinator = coordinator,
        sourceId = "file-42",
        payload = file,
        onClick = { openFile(file) },
        onDragStart = { event -> showDraggingState(event) },
        onDrag = { event -> updatePreview(event) },
        onDragEnd = { event -> commitMove(event) },
        onDragCancel = { event -> restoreState(event) }
    )
)
~~~

声明后自动获得：

| 能力 | 触发条件 | 回调 |
|---|---|---|
| 轻触点击 | 未确认重触，正常抬起 | onClick |
| 重触开始 | PRESS + heavy 且置信度达标 | onDragStart |
| 重触移动 | 已进入 DRAGGING 的 MOVE | onDrag |
| 重触结束 | 已拖动后正常抬起 | onDragEnd |
| 取消 | 多指、失焦、取消、超阈或卸载 | onDragCancel |

Modifier 内部负责：

- 注册和注销 HeavyDragSource；
- 在布局变化时更新 bounds；
- 将当前拖动位移映射到 graphicsLayer；
- 结束或取消时恢复位移；
- 使用 rememberUpdatedState 保持最新回调。

组件不需要直接调用 SDK，也不需要自行判断轻触还是重触。

### 3.3 声明拖放区

~~~kotlin
Box(
    modifier = Modifier.heavyDropTarget(
        coordinator = coordinator,
        targetId = "knowledge-base",
        accepts = { payload -> payload is KnowledgeItem },
        onEnter = { event -> highlight(true) },
        onOver = { event -> updatePreview(event) },
        onExit = { event -> highlight(false) },
        onDrop = { event -> saveToKnowledgeBase(event.payload) }
    )
)
~~~

Drop Zone 的语义是“释放时提交”，正常顺序为：

~~~text
onEnter -> 0..N 次 onOver -> onExit 或 onDrop
~~~

目标可用 accepts(payload) 拒绝不支持的数据；priority 和 zIndex 用于目标选择。

### 3.4 声明重叠目标

~~~kotlin
Box(
    modifier = Modifier.heavyOverlapTarget(
        coordinator = coordinator,
        targetId = "task-card",
        overlapEnterThreshold = 0.20f,
        overlapExitThreshold = 0.10f,
        accepts = { payload -> payload is KnowledgeItem },
        onEnter = { event -> showOverlapState(true) },
        onOver = { event -> updateOverlapRatio(event.overlapRatio) },
        onExit = { event -> showOverlapState(false) },
        onCommit = { event -> bindToTask(event.payload) }
    )
)
~~~

Overlap Target 与 Drop Zone 的区别：

- Drop Zone 主要判断拖动锚点或拖动源中心是否位于目标区域内，释放后提交。
- Overlap Target 计算拖动源矩形与目标矩形的交集比例，可同时命中多个目标。
- 进入阈值和离开阈值分开设置，用于抑制边界抖动。

## 5. SDK 与拖拽系统的解耦判断

### 5.1 依赖方向

~~~text
aispect-touch-android AAR
        <- 只被 App 防腐层调用
AispectHeavyTouchBridge
        -> 输出 HeavyTouchClassifierGateway
HeavyDragRuntime
        -> HeavyDragCoordinator
        -> Compose/View/Overlay 适配层
        -> 业务组件回调
~~~

实际依赖方向是单向的：

- SDK 不引用 com.paifa、SuperApp、HeavyDrag 或业务对象。
- Core 不引用 Android、Compose、SDK 或 AAR 包名。
- Accessibility 只接收通用 HeavyDragRuntime，不知道 Aispect 类型。
- App 的组合根才同时知道 Aispect 和 HeavyDrag。

### 5.2 有意存在、且可接受的耦合

1. AispectHeavyTouchBridge 依赖 SDK 公共 API：这是适配器职责。
2. UniVergeApplication 选择 Aispect classifier：这是组合根职责。
3. 业务组件依赖 HeavyDrag 事件类型和 Modifier：这是声明功能所必需的耦合。
4. App 依赖本地 AAR 文件：这是制品级耦合，不是源码反向依赖。

## 7. 状态机和终态合同

~~~mermaid
stateDiagram-v2
    [*] --> IDLE
    IDLE --> PRESSED_PENDING: DOWN 命中 source
    PRESSED_PENDING --> PRESSED_PENDING: 普通 MOVE/等待分类
    PRESSED_PENDING --> IDLE: UP + 轻触，提交 onClick
    PRESSED_PENDING --> DRAGGING: 重触 + 置信度达标
    PRESSED_PENDING --> IDLE: 超阈移动/超时/多指/CANCEL
    DRAGGING --> DRAGGING: MOVE，更新 source 和 target
    DRAGGING --> IDLE: UP，提交 drop/overlap/onDragEnd
    DRAGGING --> IDLE: 多指/失焦/CANCEL/卸载
~~~

必须保持：

1. 一次手势最多一个 source。
2. 一次手势最多一个 onDragStart 和一个终态回调。
3. 旧 gestureId 的分类结果不能启动下一次手势。
4. 轻触不能改变 source 位移。
5. 重触未确认前不能触发拖动回调。
6. 所有取消路径都清除 active session、目标候选和临时引用。
7. 分类器与协调器在超阈、多指、失焦和关闭时都收到终止信号。

## 8. 坐标、命中和优先级

| 场景 | 坐标约定 |
|---|---|
| 同一 Compose Root | boundsInRoot() 转换为 Host 局部坐标 |
| 同一 Android Window | Window 坐标 |
| 无障碍/悬浮 Overlay | 先转换到同一屏幕坐标再比较 |
| 跨 App | 不使用本系统几何命中，另行采用系统 DragEvent |

目标筛选顺序：

~~~text
enabled
-> accepts(payload)
-> 有效 bounds
-> priority
-> zIndex
-> 几何命中
-> 注册顺序
~~~

- Drop Zone 默认以拖动源中心或配置的锚点判定。
- Overlap Target 使用 AABB 交集比例。
- 不允许直接比较不同坐标空间的矩形。
- bounds 无效或过期时不提交 drop/overlap 事件。

## 9. 生命周期、线程和性能

- MotionEvent 入口在 UI 线程，但只做轻量事件转换和状态判断。
- SDK 模型加载、推理、窗口特征预处理、归一化和样本 JSON 写盘在后台线程。
- Compose Host 的 motionEventSpy 只观察，普通点击和列表滚动不在 ACTION_DOWN 时被抢占。
- 重触确认后，pointer input 才消费拖动阶段变化。
- Provider 使用租约管理 Runtime；最后一个宿主释放租约时关闭 Runtime。
- 组件卸载时注销 source/target，防止旧 bounds 和回调残留。
- 模型更新在活动触摸期间延迟激活，当前触摸继续使用原模型。

## 10. 内聚性与耦合风险

### 10.1 高内聚部分

- Coordinator 集中管理手势状态、取消原因、目标命中和事件顺序。
- SDK 只负责触摸分类，不承担拖动、目标选择或业务提交。
- Modifier 只负责注册、布局边界和视觉位移，不复制分类逻辑。
- 目标组件只关心进入、离开和提交，不知道模型如何推理。

### 10.2 尚未达到完全低耦合的原因

- App bridge 同时知道 SDK 类型和 HeavyDrag 类型，这是组合适配的必要耦合。
- payload 使用 Any?，业务类型检查发生在运行时。
- 一个 Coordinator 当前只有一个活动 session；多个窗口共用 Runtime 时需要额外隔离。
- DisposableEffect 的配置变化可能导致 source 注销和重新注册。
- 传统 View 一旦拦截了当前事件流，Android 不允许把同一流重新交回子 View。

## 11. 已知问题与改进优先级

### 高优先级

1. 传统 View Host 事件所有权：HeavyDragHostView 在 source DOWN 时拦截；当前流即使取消也不能重新交给子 View。生产 Compose 路径使用观察式 Host，但 View 适配器仍应限制使用范围或改为延迟接管。
2. 旧后台任务通常是“丢弃结果”而非“立即停止计算”：快速连续触摸时，旧任务仍可能占用 CPU。后续应增加可取消任务或队列合并。
3. 模型激活的文件切换、catalog reload 和可加载性检查应继续做线程边界审计。

### 中优先级

1. 将 Any? payload 替换为带类型标签的泛型或稳定序列化 payload 合同。
2. 为每个 Window/Overlay 建立独立 Coordinator，禁止跨窗口共享活动 session。
3. 将 source 注册配置与动态回调分开，减少重组造成的注销/重注册。
4. 增加真实 Compose LazyColumn 集成测试：普通滑动、普通点击、重触拖动后立即点击其他控件。
5. 增加 Overlay 坐标变换以及旋转、滚动、窗口尺寸变化测试。

### 低优先级

1. 目标数量很大时引入空间索引，减少每个 MOVE 扫描全部目标。
2. 将旧 univerge-touch 目录标记为 compatibility-only，避免维护者误把它当成当前 SDK 源码。

## 13. 新组件接入验收清单

接入一个新的可重触拖动 UI 时，逐项确认：

- [ ] 位于已有 HeavyDragHost 内。
- [ ] 使用稳定且唯一的 sourceId。
- [ ] payload 生命周期明确，最好是不可变对象。
- [ ] 轻触回调不会移动组件。
- [ ] 只有 onDragStart 后才改变组件位置。
- [ ] 必要时声明 accepts，拒绝不支持的 payload。
- [ ] Drop Zone 和 Overlap Target 选择了正确语义。
- [ ] bounds 在滚动、旋转和尺寸变化后仍能更新。
- [ ] onDrop/onOverlapCommit 具备幂等处理。
- [ ] onDragCancel 能恢复视觉和临时业务状态。
- [ ] 组件卸载后 source/target 已注销。
- [ ] 普通点击、列表滚动和其他控件点击回归通过。

## 14. 最终判断

当前实现已经不是测试页专用的重触方块逻辑，而是一套可复用的声明式拖拽基础设施：

~~~text
SDK 负责识别力度
Core 负责决定手势语义
Adapter 负责接入平台事件和布局
UI 负责声明 source/target
业务负责处理回调
~~~

因此，新增组件通常不需要修改 SDK、Runtime 或 Coordinator，只需要在正确的 Host 内声明 Modifier 并实现业务回调。只有当需求改变事件所有权、坐标空间、手势并发模型或分类结果合同本身时，才需要修改底层模块并重新评审本文件。
