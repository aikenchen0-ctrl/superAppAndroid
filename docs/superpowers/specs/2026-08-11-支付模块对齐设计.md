# Android 悬浮聊天支付模块对齐设计

## 目标

在悬浮聊天 SCRM 模块中复现 iOS 支付流程：支付工具进入 Composer，确认页展示金额/备注/钱包信息，提交后进入异步任务状态，支付卡片点击后读取详情和状态。真实支付、领取、转账请求只保留调用逻辑，不在自动化测试中触发。

## 接口范围

- `POST /payments/lucky-money`
- `POST /payments/lucky-money/take-by-message`
- `POST /payments/red-packets/detail-by-message`
- `POST /payments/red-packets/status-by-message`
- `POST /payments/remittance`
- `POST /payments/transfers/take-by-message`
- `POST /payments/wallet-balance`
- `GET /tasks/{taskId}`（异步任务终态）

所有支付写接口通过 `Idempotency-Key` 传递幂等键；请求模型只保留接口文档中的公开字段。支付密码仅存在于内存请求对象中，不持久化、不写日志。

## Android 结构

1. `ScrmModels.kt` 增加支付请求模型和统一支付数据读取模型。
2. `ScrmApiClient.kt` 增加 `ScrmPaymentApi`，统一封装路径、JSON 和幂等键。
3. 新增纯 Kotlin `PaymentFlow.kt`，负责金额分/元转换、任务状态映射、详情状态映射和 Composer 请求校验。
4. 支付卡片详情浮层使用状态模型驱动：加载中、可领取、已领取、已领完、失败可重试、任务处理中。
5. Composer 确认页先生成请求和幂等键，再由现有 UI 回调交给人工执行；自动化测试只验证请求 JSON、路由和状态解析。

## 安全与测试边界

- 不在单测、构建脚本或 UI 初始化中调用真实支付/领取/转账接口。
- 只使用 fixture transport 验证 GET/POST 请求组装与响应解析。
- `unknown` 任务状态禁止自动重发，UI 必须提示人工核对。

## 验收标准

- 支付请求字段与接口文档一致，幂等键每次新业务意图唯一。
- 任务状态能稳定映射 processing/success/failed/unknown。
- 红包、转账详情状态能驱动卡片和全屏详情浮层文案。
- 钱包余额可展示 loading/success/error 三态。
- 编译通过，进度文档记录本阶段完成项；不执行真实支付请求。
